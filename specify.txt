1. 개요
--------------------------------------------------------------------------------
1.1 목적
  로그인한 사용자가 (a) 텍스트 시나리오(프롬프트), (b) 정지 이미지(사진), 또는
  (a)+(b)를 입력하면, 캡션과 오디오가 포함된 동영상(MP4)을 생성해 주는
  클라이언트-서버 웹 서비스를 제공한다.

1.2 릴리스 범위
  릴리스 1 [구현] : 입력 3모드, 장면 분해, 사진-장면 매핑, 샷 생성(재시도 1회),
                    순서대로 연결, 진행률(SSE), 작업 목록/삭제/취소, 보관 기간,
                    인증(이메일 6자리 코드), 인앱 메일함, 한/영 UI, 엔진 선택과
                    클라우드 엔진 동의.
  릴리스 2 [R2]   : 타임라인 합성기, 장면 전환, 사진별 안내 프롬프트 -> 캡션,
                    자막(SRT/ASS/번인), slideshow 엔진, 배경음악.
  릴리스 3 [R3]   : TTS 내레이션과 덕킹, 단어 하이라이트 자막, 비율 프리셋,
                    스토리보드 검토-수정-렌더, 샷 재생성, 템플릿.

2. 용어
--------------------------------------------------------------------------------
  Job          사용자 1회 요청. 입력, 옵션, 상태, 최종 영상을 가진다.
  SourceImage  업로드 사진 1장. 순서(position), 대체 텍스트(alt text), [R2] 안내 메모.
  Scene        시나리오 분해 결과 1개 장면. 설명(영상 프롬프트), 길이, 매핑된 사진.
               [R2] 캡션, 내레이션, 전환, 모션, 타임라인 위치.
  Shot         Scene 1개를 엔진으로 생성한 클립 1개. 상태, 시도 횟수, 클립 경로.
  Provider     영상 생성 엔진 어댑터 (VideoProvider 프로토콜).
  Timeline     [R2] 장면별 시작/길이/전환/자막/오디오 위치를 계산한 결과.
  계획 길이    planned_seconds = Σ Scene.duration_seconds (전환 겹침 차감 전).

3. 입력 모드
--------------------------------------------------------------------------------
  - TEXT_ONLY   : 시나리오만 -> 장면 분해 -> 장면별 T2V
                  (chain_frames=on 이면 2번째 장면부터 이전 샷 마지막 프레임으로 I2V)
  - IMAGE_ONLY  : 사진만     -> 사진 1장당 장면 1개, 기본 모션 프롬프트로 I2V
                  [R2] 사진별 안내 메모가 있으면 그것으로 모션 프롬프트/캡션 생성,
                       slideshow 엔진 선택 시 GPU 없이 Ken Burns 영상.
  - TEXT_IMAGE  : 시나리오 + 사진 -> n번째 사진을 n번째 장면에 매핑해 I2V.
                  남는 장면은 chain_frames 규칙(FR-009), 남는 사진은 미사용 개수 보고(FR-010).

5. 시스템 아키텍처
--------------------------------------------------------------------------------
  [Client: React 18 + TypeScript (Vite) SPA, 한/영 i18n]
     │  REST (세션 쿠키 + CSRF 헤더) + SSE (진행률)
     ▼
  [API Server: FastAPI]
     ├─ DB: SQLite(개발 기본) / MySQL 9.3(docker compose)   ※ PostgreSQL 전환은 16장 #9
     ├─ Storage: ./storage/jobs/<job_id>/ (로컬)  ※ MinIO/S3 전환은 R3
     ├─ 내장 메일 서버: aiosmtpd :1025 -> sent_emails 테이블 -> 인앱 메일함 API
     │  작업 큐잉
     ▼
  [Broker: Redis 7] ←→ [Celery Worker (GPU 노드, --pool=solo, concurrency=1)]
                     ←→ [Celery Beat: 매시 정각 보관 기간 만료 정리]

  워커 파이프라인 (server/worker/tasks.py: run_job)
    1. 계획      split.py(장면 분해) + mapping.py(사진-장면 매핑)   ※ API 접수 시 수행 [구현]
                 [R2] captions.py: 사진별 안내 메모/이미지 -> 캡션·내레이션·모션 프롬프트
                 [R3] review=true 면 status=planned 로 정지, 사용자 수정 대기
    2. 샷 생성   장면마다 provider.generate(), 실패 시 1회 재시도 [구현]
                 chain_frames: frames.py 로 이전 샷 마지막 프레임 추출 [구현]
                 [R3] 샷 캐시(cache_key)로 변경 없는 샷 재사용
    3. 오디오    [R2] 배경음악 준비  [R3] TTS 내레이션 -> 장면 길이 보정
    4. 타임라인  [R2] timeline.py: 6장 규칙으로 장면 위치 계산, Scene 에 기록
    5. 합성      [구현] join.py: concat(스트림 복사, 실패 시 재인코딩)
                 [R2] compose.py: Timeline -> FFmpeg filter graph (정규화/전환/자막/오디오)
                      -> final.mp4 (+ subtitles.srt / .ass)

  설계 원칙
  - 엔진은 VideoProvider 프로토콜과 registry 로만 접근한다. 엔진 이름은
    worker/providers 밖에 나오지 않는다(FR-016). 클라이언트는 GET /api/providers 목록만 쓴다.
  - 샷 단위 생성 후 연결: 엔진 1회 생성 길이(5~10초) 한계를 넘기 위함.
  - 생성은 항상 비동기 작업. API 는 작업 ID 를 즉시 반환한다(FR-024).
  - [R2] 시간 계산은 timeline.py 한 곳에서만 한다. compose/자막/오디오는 Timeline 값만 쓴다.
  - [R2] 생성(비싼 단계)과 합성(싼 단계)을 분리한다. 캡션/전환/음악만 바뀌면
    샷을 재생성하지 않고 재합성만 한다.

6. 타임라인 모델 [R2]
--------------------------------------------------------------------------------
6.1 계산 규칙
  - 장면 i 의 길이 d_i = min(Shot 실측 길이, Scene.duration_seconds).
    (ShotResult.duration_seconds 는 파일에서 측정한 값이다.)
  - 장면 i 로 들어오는 전환 길이 t_i: 장면 0 은 0, transition=none 이면 0.
    t_i = min(transition_seconds, d_{i-1}/2, d_i/2).
  - 시작 시각: s_0 = 0,  s_i = s_{i-1} + d_{i-1} - t_i
  - 최종 길이: T = s_last + d_last  (= Σd_i - Σt_i, 계획 길이보다 짧거나 같다)
  - 자막 큐 i: [s_i + t_i/2, s_{i+1} + t_{i+1}/2), 마지막 큐는 T 까지.
  - 오디오: 내레이션 i 는 s_i + t_i 에서 시작. 배경음악은 0~T 전체.
  - 타이틀/엔딩 카드(FR-049)도 장면 1개로 취급한다.
  - FR-032(3분 상한)는 계획 길이(Σ Scene.duration_seconds, 카드 포함)로 판정한다.
6.2 합성 그래프 (FFmpeg)
  - 입력 정규화: scale/pad(fit) 또는 crop(fill) -> setsar=1 -> fps -> format=yuv420p
    -> trim=duration=d_i -> settb=AVTB.   ※ FR-013 을 이 단계에서 보장한다.
  - 연결: t_i>0 이면 xfade(transition, duration=t_i, offset=s_i),
          t_i=0 이면 concat(n=2). 장면마다 섞어 쓸 수 있다.
  - 자막: SRT/ASS 생성 후 subtitles 필터로 번인(옵션). 폰트 경로는 server/assets/fonts.
  - 오디오: 내레이션 adelay 배치 -> 배경음악 aloop/atrim/afade -> sidechaincompress(덕킹)
    -> amix -> loudnorm(-14 LUFS). 오디오 소스가 없으면 오디오 트랙을 만들지 않는다.

7. 기능 요구사항
--------------------------------------------------------------------------------
7.1 릴리스 1 [구현]  (원문: specs/001-movie-video-generation/spec.md)
  입력
    FR-001 시나리오, 사진, 또는 둘 다로 작업 생성.
    FR-002 둘 다 없으면 거부(400 no_input).
    FR-003 사진 JPG/PNG/WebP, 장당 20MB 이하.
    FR-004 작업당 사진 1~100장. 초과 시 한도를 밝혀 거부.
    FR-037 사진마다 대체 텍스트(최대 500자) 입력·저장.
  장면 분해
    FR-005 시나리오 -> 순서 있는 장면 목록(설명, 길이).
    FR-006 고급 분해(LLM) 불가/실패 시 문단 분해로 대체하고 작업은 계속.
    FR-007 시나리오의 어떤 부분도 말없이 누락하지 않는다.
  사진 매핑
    FR-008 n번째 사진 -> n번째 장면.
    FR-009 장면이 더 많으면: chain_frames=off 는 마지막 사용 사진, on 은 이전 샷 마지막 프레임.
    FR-010 사진이 더 많으면 미사용 사진 수를 알리고 작업 완료.
    FR-011 사진만 있으면 사진 1장당 샷 1개, 기본 모션 설명 사용.
  생성/연결/엔진
    FR-012 장면마다 샷 1개 생성, 순서대로 연결해 MP4 1개.
    FR-013 연결 전 모든 샷을 같은 해상도·프레임레이트로 정규화.  (16장 #2)
    FR-014 해상도, 샷당 길이, fps 설정. 미설정 시 기본값(832x480, 5초, 16fps).
    FR-015 샷마다 이전 샷 마지막 프레임 이어 쓰기 여부(chain_frames) 선택.
    FR-016 엔진 교체는 설정만으로(코드 변경 없음).
    FR-035 작업마다 활성 엔진 중 선택(LTX-2.3 기본, Gemini). 키보드 조작 가능.
    FR-036 클라우드 엔진 제출 전 외부 전송을 텍스트로 고지, 명시적 동의, 동의 시각 기록.
  상태/진행률
    FR-017 상태: queued, running, succeeded, failed, expired.  ([R3] planned 추가, FR-057)
    FR-018 진행률 0~100 정수 + 짧은 단계 메시지.
    FR-019 진행률을 새로고침 없이 푸시(SSE).
    FR-020 페이지를 떠났다 돌아와도 상태 유지.
  결과
    FR-021 성공 시 MP4 다운로드.
    FR-022 샷 목록(원 장면 발췌, 상태) 표시.
    FR-023 내 작업 목록, 최신순.
    FR-038 보관 기한 전 내 작업 삭제. queued/running 은 삭제 불가.
    (취소) POST /api/jobs/{id}/cancel 로 queued/running 작업 중지 [구현, spec.md 미반영: 16장 #5]
  처리/신뢰성
    FR-024 백그라운드 생성, 제출 즉시 작업 ID 반환.
    FR-025 작업당 시간 제한(기본 30분), 초과 시 failed.
    FR-026 생성 자원당 작업 1개씩, 나머지는 대기열.
    FR-027 실패 시 어느 샷이 실패했는지 알림.
    FR-033 샷 실패 시 1회 자동 재시도, 재시도도 실패해야 작업 실패.

11. 비기능 요구사항
--------------------------------------------------------------------------------
11.1 성능 (constitution IV)
  - 생성 외 API 응답 p95 300ms 이하(기준 부하: 동시 사용자 5명).
  - 접수 응답 1초 이내(SC-004), 진행률 10초 이내 간격(SC-003).
  - 모델은 1회 로드 후 재사용. 요청마다 로드 금지.
  - plan.md 마다 변경 경로의 예산(p95, 메모리/VRAM, 출력 1초당 생성 시간)을 적는다.
    예산 10% 초과 변경은 사유 없이 병합 금지.
  - [R2] 재합성(전환/자막/음악)은 GPU 를 쓰지 않는다.
11.2 신뢰성
  - 작업 시간 제한 30분(TASK_TIME_LIMIT_SECONDS), soft limit 은 30초 전.
  - 생성 자원 1개당 작업 1개(worker concurrency=1, Windows 는 --pool=solo).
  - 샷 1회 자동 재시도. ProviderError.transient 로 일시/영구 오류 구분.
11.3 보관/개인정보
  - 작업 생성 2일 후 업로드 사진, 샷, 최종 영상, [R2] 자막·업로드 음원 삭제(매시 정리).
  - [R2] 업로드 사진의 EXIF GPS 는 저장 시 제거([R3] EXIF 촬영 시각은 정렬용으로 별도 보관).
  - 외부 서비스(클라우드 엔진, 외부 LLM)로 사용자 데이터를 보낼 때는 고지·동의 후에만(FR-036, FR-046).
11.4 보안
  - 비밀번호 12자 이상, Argon2id 해시. 세션 7일. CSRF 토큰.
  - 비밀값(API 키, SESSION_SECRET)은 server/.env 로 관리, 저장소 커밋 금지.
  - 개발용 기능(debug_code, 공개 메일함, mock 엔진, 종료 API)은 ENV=development 에서만.
11.5 접근성 (constitution III, WCAG 2.2 AA)
  - 모든 조작 키보드 가능, 접근 가능한 이름 필수. 본문 대비 4.5:1, 큰 글자/경계 3:1.
  - 오류는 텍스트로, 색만으로 상태 전달 금지.
  - 사진마다 대체 텍스트 입력 가능. 내레이션 영상은 자막 필수.
  - UI 변경마다 자동 접근성 검사 + 키보드/스크린리더 수동 점검 1회.
11.6 업로드 제한
  - 이미지 jpg/png/webp 장당 20MB, 작업당 100장. [R2] 음원 mp3/wav/m4a 30MB.
  - 계획 길이 180초 이하.

  배포   : Dockerfile(멀티 스테이지), compose.yaml(Traefik, MySQL, Redis)
